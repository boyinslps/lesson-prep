# 學習單資料與提交規範（識別欄 · 題型標註 · 繳交 · 即時同儕動態 · 教師模式）

> 這份文件定義**所有互動學習單**（不論用共用套件 `student-submit.js` 或客製 JS）都必須遵守的
> **資料契約**：學生是誰、每題是什麼類型、繳交時送出什麼形狀的資料。
>
> **定位**：`HTML互動教材設計規範.md`／`互動教材進階規範.md` 談「頁面怎麼設計」；
> **這份談「頁面產出的資料要長什麼樣子」**——是評分平台（`評分平台/`）能讀懂任何學習單的前提。
>
> **適用範圍**：本規範制定後，**所有新學習單一律照此實作**；既有學習單（如五上 L01）已依此規範改版，作為範例。

## 1. 識別列（Identity Bar）——放在學習單最上方

**原則**：學生是誰，用**三個數字**唯一決定，不問姓名。

| 欄位 | 說明 | 限制 |
|---|---|---|
| 年級 | 4／5／6… | 只能輸入數字 |
| 班級 | 例：1（代表 1 班） | 只能輸入數字 |
| 學號 | 班級座號/學號 | 只能輸入數字 |

- **位置**：頁面最上方（`<body>` 一開始、標題之前），學生一進頁面就先填，不是繳交時才問。
- **輸入限制**：`inputmode="numeric"` ＋ JS 過濾非數字字元（`input` 事件即時剔除）；三欄都必填才能繳交。
- **持久化**：填過一次存 `localStorage`（key 建議 `wk_identity`），重新整理不必重填。
- **為什麼不問姓名**：三個數字組成的識別碼已可唯一定位到某位學生，且對「即時同儕動態」（§4）天然帶一點匿名感；要姓名的場景（如需要對應 Google Classroom 帳號回寫成績）由教師端**另外**匯入名單／學號對照解決，不需要學生在學習單裡重複輸入姓名。

**參考實作**：`評分平台/student-submit.js` 的 `StudentSubmit.init()` 會自動在掛載點注入這個識別列；客製頁面（如 L01）可直接仿造其 DOM／驗證邏輯手刻，只要資料契約一致即可（見 §3）。

## 2. 題型標註——每個互動元素都要宣告自己是哪一種

**題型只有三種**（2026-09-16 教師定案收斂）：`experience`／`score`／`open`，**每一個作答元素都必須標**。
「加分題」**不是第四種題型**，而是疊在這三種之上的一個**標記**（見下面 2-b）。

| 題型 | 代碼 | 特徵 | 送 AI 評分？ | 計入正確率？ | 計入完成度？ |
|---|---|---|---|---|---|
| **測驗題** | `score` | 有正確答案，且**這節課要正式評量** | ❌ | ✅ 算 | ✅ 算 |
| **體驗題** | `experience` | 有正確答案（可即時告訴學生對不對），但**這節是體驗/暖身，不正式計分** | ❌ | ❌ 不算 | ✅ 算 |
| **開放題** | `open` | 沒有標準答案，學生寫自己的想法/推論 | ✅ **只有這種送** | ❌ 不算 | （原文照送，供 AI／教師評分） |

**為什麼只有 `open` 送 AI**：`score`／`experience` 本來就有標準答案、學習單端已經判好 `isCorrect`，
送給 AI 既浪費 token，又可能讓 AI 判出跟標準答案不一致的結果。判斷準則、評分總則全文見 **《AI評分規範》**。

**判斷準則（換單元一樣適用）——先問「這節課的定位」，不是看「題目形式」**：
- 這節課的定位是「正式檢核學到了沒」→ 用得到的客觀題標 `score`。
- 這節課的定位是「先接觸、有感、建立直覺」（像 L01 這種第一節引發問題意識的課）→ 即使題目有標準答案，也標 `experience`，不計分——**呼應「先讓學生被打臉、不是被打分數」的教學意圖**。
- 沒有標準答案、要看學生自己怎麼想 → `open`。

### 2-a. 標註方式（DOM 慣例）

每個作答元素或其容器加兩個 data 屬性：
```html
<div data-qid="q1" data-qtype="experience" data-correct="true">…</div>
<div data-qid="q9" data-qtype="open">…</div>
<div data-qid="q2" data-qtype="score" data-correct="B">…</div>
```
- `data-qid`：題目代號，同一份學習單內唯一。
- `data-qtype`：`score` / `experience` / `open` 三選一（**必填**）；是加分題的話另外加 `data-bonus="1"`。
- `data-correct`（`open` 不用）：標準答案，供頁面自己即時比對；多選用「、」分隔。

**客製 JS 頁面（如 L01）**：若頁面已經用自己的資料結構管理題目與正解（例如 L01 的 `items[i].real`），**不必**硬套 data 屬性，但**繳交時組出的 payload 必須符合 §3 的欄位形狀**——資料契約優先於實作手法。

### 2-b. 加分題＝標記，不是題型

**加分題是「基於三種題型之一的額外加分題目」**——它仍然有自己的 `qtype`（三選一），
另外用 `bonusQids` 標記「這幾題是加分題」。規則：

- **不進任何分母**：`accuracyRate`、`experienceCompletion` 的分子分母都不算它，
  避免「要不要寫加分題」影響完成度統計。
- **不進扣分池**：加分題答錯／沒寫**不扣分**，只有寫得好才**往上加**——這是「加分」的定義。
- **分數是額外疊加**：加在最終總分之上，允許 `totalScore` 超過 100（見 `../評分平台/SPEC.md` §7-f）。
- **誰給分**：
  - `score`／`experience` 型加分題 → 看 `isCorrect`，對就加該題配分。
  - `open` 型加分題 → **只要是開放題就送 AI**（2026-09-16 教師定案：不分是不是加分題），
    答案要**同時放進 `openAnswers` 與 `bonusAnswers`**——`openAnswers` 讓它送去 AI 評分，
    `bonusAnswers.{qid}.completed` 供學生端顯示完成提示。AI 收到題目時已經知道哪些 qid 是加分題
    （伺服器依 `bonusQids` 參數拆成「主要開放題」與「加分題」兩組分別送），
    加分題依內容完整度給 0～3 分（不是照一般開放題的規準分），**跟主要開放題的分數各自獨立、不會互相影響**，
    教師端仍可在批改抽屜手動覆蓋 AI 給的加分等級。詳見 `../評分平台/SPEC.md` §7-f／§7-h。
- **學生端要有完成提示**：類似「🎁 加分題：已完成／尚未完成」的小標籤，
  讓學生知道自己有沒有寫，但**不顯示會加幾分**（那是老師事後才決定的事）。

> **「不計分」是指不進正確率，不是「不影響成績」**（2026-09-09 教師定案分數計算後補充，容易誤會，特別寫清楚）：
> 上表的「計入正確率」欄講的是頁面自己算的 `accuracyRate`——那個欄位的分母**只有 `score` 題**，`experience` 題確實不進去。
> 但**教師端的最終成績（`totalScore`）是另一套計算**：評分平台預設把 `score` 與 `experience` **合在一起**當扣分池，逐題看 `isCorrect`，錯一題扣一分（見 `../評分平台/SPEC.md` §7-d）。
> 也就是說**體驗題答錯一樣會扣最終分**——L01 就是這樣：全部 8 題都是 `experience`、`accuracyRate` 是 `null`，但「全對 100 分、錯一題 99 分」正是教師要的行為。
> **所以標 `experience` 的理由是「這節的定位是體驗、不要拿正確率當成績」，不是「這題怎麼答都無所謂」**；真的不想影響成績的題目，別給它 `data-correct`／別把 `isCorrect` 判成 `false`，或直接標成 `open`。

### 2-c. 未來標準：每題都要有題號＋可自訂配分（2026-09-15 教師定案，只套用在此後新建的學習單）

**現況（2026-09-16 更新）**：非開放題（`score`／`experience`）可逐題覆寫扣分（`itemPoints`，見 `../評分平台/SPEC.md` §7-d）；開放題已改成**每題各自送 AI 獨立打分**（見《AI評分規範》§7），但每題預設**同權重平均**，還沒有「這題開放題比較重要、該佔比較多分」的可調欄位；加分題是額外疊加的 0～3 分（見 §2-b），同樣每題平權相加。也就是說**打分粒度**（逐題各自評）已經做到了，但**配分粒度**（逐題可調整各佔多少分）還沒有。

**未來標準**：此後新建立的學習單，**每一題**（`score`／`experience`／`open`，含加分題）都要：
1. 有自己的**題號**（`qid`，本來就必填，見上）；
2. 對應一個**可由 admin（教師）編輯的配分／權重欄位**，而不是像現在開放題只能「同權重平均」。

**範圍**：這是**評分平台端**（`評分平台/teacher.html` 的「學習單設定 → 分數計算」）要擴充的資料結構與 UI，**不是**要求每份學習單自己實作配分邏輯——學習單端只要老實標好 `qid`／`qtype`／`bonusQids`（本規範既有要求），配分由教師端統一管理。

**現有學習單不用改**：五上 L01 等既有學習單維持現行整體 `openWeight`／同權重平均制，**不回頭補**逐題配分；此標準只約束「之後照新標準建立」的學習單。實作時機：等到真的有教師要求「某題開放題該佔比較多分」時才動工。

### 2-d. 自由文字題的自動核對：正則表達式（2026-09-21 教師定案）

有些題目要學生**自己打字填答案**（例如「找出一個中西區的景點」），答案因人而查、可能有多個都對，無法像選擇題那樣寫死單一 `data-correct`。做法：**讓教師在 `#admin` 用「正則表達式」當標準答案**，學習單用 `new RegExp(pattern,'i').test(學生作答)` 判 `isCorrect`。

- **教師怎麼填＝直接打進學生作答的那個輸入框**：`#admin` 下該作答框就是答案 key 欄，不另外開一區設定欄——學生看到的欄位跟教師輸入答案的欄位是同一個。學生不會打正則、也不必區別。按「⬆ 上傳答案」把每題 pattern 存進 `quizzes/{quizId}.surveyPatterns:{qid:pattern}`。
- **多個答案都對**：用 `|` 分隔，例如 `黃金海岸|成功國小蝴蝶園`。`test()` 是**子字串比對**（不是完全比對），學生答案只要**含**其中一個關鍵詞就算對。
- **留空＝不判對錯**：某題沒設 pattern 時，退回「有沒有填」當 `isCorrect`（呼應體驗題「重點是有沒有參與」）。
- **無效的正則**要 `try/catch` 包起來（教師可能打錯），失敗時 `console.warn` 並退回「有沒有填」判斷，不可整頁壞掉。
- **不牴觸 §5-3「標準答案只有一個來源＝學習單自己」**：pattern 存在學習單自己的資料流（`quizzes/…`），評分平台不碰、也不重複維護。

## 3. 繳交資料契約（Firestore：`submissions` 集合）

**文件路徑**：`submissions/{worksheetId}__{grade}-{className}-{studentId}`
（同一位學生重繳＝覆蓋同一份文件，`{grade}-{className}-{studentId}` 例：`5-1-12`）

```jsonc
{
  "worksheetId": "g5-L01",
  "worksheetTitle": "假消息與目的辨識",
  "lessonPath": "g5/L01",

  "grade": 5, "className": 1, "studentId": 12,        // 識別列，皆為 number

  "answers": { "q1": true, "q9": "我會先查證再相信" },  // 扁平版：所有題目原值，供舊版介面/快速預覽
  "qtypes": { "q1": "experience", "q9": "open", "q10": "open" },  // 每題的題型：score/experience/open 三選一
  "bonusQids": ["q10"],                                 // 哪幾題是加分題（疊在題型之上的標記，見 §2-b）

  "scoreAnswers":      { "qidX": { "given": "B", "correct": "B", "isCorrect": true } },
  "experienceAnswers": { "q1":   { "given": true, "correct": true, "isCorrect": true } },
  "openAnswers":       { "q9": "我會先查證再相信" },
  "bonusAnswers":      { "q10": { "given": "我會看是誰發的", "completed": true } },  // 有 bonus 題才需要這欄；不含分數（見 §2）

  "accuracyRate": null,          // 量化正確率：round(correct score 題/總 score 題*100)；沒有 score 題＝null
  "experienceCompletion": 88.9,  // 體驗完成度：round(已作答體驗題/總體驗題*100)

  "status": "submitted",
  "submittedAt": "<serverTimestamp>"
}
```

**欄位規則**：
- `accuracyRate`：分母＝`score` 題總數；分母為 0 時整欄位是 `null`（不是 0，避免誤讀成「考了 0 分」）。
- `experienceCompletion`：分母＝`experience` 題總數；衡量「有沒有作答」，不是「答對了沒」——正確與否記在 `experienceAnswers[qid].isCorrect`，不影響這個百分比。
- **`isCorrect` 是教師端算成績的唯一依據，每題都必須確實填對**（不是給人看的參考欄位）：評分平台的最終分＝滿分減掉「每個 `isCorrect===false` 的題目」的扣分（見 `../評分平台/SPEC.md` §7-d）。因此：
  - **沒作答也要輸出這一題**，且 `isCorrect` 判成 `false`（不是省略、不是 `null`）——省略了那題就等於「沒扣到分」，學生空著反而不會被扣。
  - **多選題**要自己定義「怎樣才算對」（全中才對？還是部分給分？），把結論落在 `isCorrect` 這個布林值上，不要把判斷推給教師端——教師端只看得到 true/false。
  - Firestore **不接受 `undefined`**：`given` 沒值時要寫 `null`，寫 `undefined` 整筆繳交會直接失敗（這個坑踩過）。
- `openAnswers`：原文字串，不做任何裁切；教師端可送 AI 評分（走 `工作台/server.py` 既有 `/api/grade`，見《AI串接窗口設定規範》），或人工看。
- `bonusQids`：字串陣列，列出哪幾題是加分題。**它們的 `qtypes` 仍然是三種題型之一**（加分是標記不是題型，見 §2-b）；沒有加分題就不必輸出這個欄位。
- `bonusAnswers`：`{ given, completed }`，`completed` 由學習單自己判斷（例如文字非空）；**不含分數**——分數（0～+3）由 AI 依內容評，教師可在評分平台事後覆蓋，見 §2-b 與 `../評分平台/SPEC.md` §7-f。`open` 型加分題的答案要**同時**放進 `openAnswers`（送 AI 用）與 `bonusAnswers`（完成度提示用），兩邊都要有。
- **正確率與 AI 是兩個獨立的計算系統，不是一個評分流程的兩步**：`accuracyRate` 由學習單自己算（客觀題）；AI 分數只評 `openAnswers`。**沒有開放題就完全不必呼叫 AI**——教師端直接拿 `accuracyRate` 當最終分即可，省一次 AI 請求也省一次等待。
- 沒有 `score` 題的學習單（如 L01——見 §5）→ `scoreAnswers={}`、`accuracyRate=null`，這是**正常狀態**，不是缺資料。

**教師端**（`評分平台/teacher.html`）讀到 `grade/className/studentId` 存在時，用它組顯示標籤（例：「5年1班12號」）取代舊的「班級/座號/姓名」欄位；兩者資料形狀不同時不必相容，因為學習單提交的身分模型已統一為本規範版本。

### 3-b. 繳交流程的學生端慣例（確認 → 繳交 → 完成獎勵）

資料形狀之外，**學生按下繳交的那一段體驗**也統一成同一套：

- **按下「繳交學習單」要先 `confirm()`**：對話框裡順便回報這次交了什麼（例如各段各答了幾題），確認後才寫進 Firestore，避免手滑誤交。
- **可以重繳**：同一位學生重繳＝覆蓋同一份文件（見上面的文件路徑），成功後把按鈕文字改成「重新繳交（覆蓋）」，讓學生知道再按一次是覆蓋而不是多交一份。
- **繳交成功才出現「完成獎勵」區塊**（2026-09-21 教師定案，此後所有新學習單一律照此實作）：
  - **為什麼**：小學生需要一個明確的「我做完了」訊號，光一行「✓ 已繳交」太弱；把課後可以玩的連結收在這個區塊裡，等於用「寫完才解鎖」把遊戲變成完成作業的獎勵，而不是上課分心的來源。
  - **怎麼做**：頁面底部放一個預設 `hidden` 的區塊（例如 `#rewardBox`），**只在寫入 Firestore 成功的 `.then()` 裡**才 `classList.remove('hidden')` 並 `scrollIntoView()`；失敗分支絕不可以顯示（沒交成功就給獎勵會讓學生以為交好了）。
  - 內容＝一句恭喜（例：「恭喜你已經做完今日的作業，可以遊玩！」）＋課後可玩的連結（打字英雄／更多遊戲…）。配色照**該份學習單自己的色系**走，不必跟別份一致。
  - **教師檢視模式（§5-7）要把它拿掉**：`applyReview()` 裡連同「繳交學習單」按鈕一起隱藏/移除——老師是在看別人的作答，不該看到獎勵區。

## 4. 即時同儕動態（Live Feed）——開放題的可選加值

**動機**：開放題常常「寫完就沒了」，看不到別人怎麼想。加一個**留言牆式**的即時動態，讓學生送出後能看到同儕的回應，強化「原來大家想法不一樣／原來我沒想到這個」的比較效果（呼應引導邏輯 G9 產出展示，但即時、同儕對同儕）。

**是否要加**：**非必要**，由該題是否「值得互相看見」決定——判準：**別人的答案會不會讓我學到東西或改變想法？** 會 → 加；單純填空核對式的開放題不必加。

**做法**：
- 集合路徑：`feeds/{worksheetId}/messages/{autoId}`。
- 文件：`{ qid, text, tag, at }`——`tag` 含年級/班級/座號（例如「5年3班12號」，2026-09-15 教師定案改成含座號，同學看得到是誰寫的，不再刻意匿名）；`text` 長度應限制（例如 ≤ 120 字）避免洗版。
  - **推送前要檢查身分已填**：跟繳交按鈕一樣呼叫 `identityValid()`，沒填年級/班級/座號就 `alert()` 提醒並擋下推送，不能送出一則沒有 `tag` 的匿名留言。
- **顯示**：固定高度、`overflow-y:auto` 的捲動容器，新留言即時進來（`onSnapshot`），數量多時只留最新 N 則（例如 50）。
- **權限**：任何已登入（含匿名）可讀可寫自己的留言；**不可修改/刪除別人的**；老師可刪除（管理不當內容）。規則見 `評分平台/firestore.rules` 的 `feeds` 區塊。
- **⚠ 複合查詢要先建索引，否則整個留言牆是靜默壞的**（2026-09-10 實測踩到）：`where('qid','==',…).orderBy('at','desc')` 這種「一個等式條件 ＋ 另一個欄位排序」屬於複合查詢，Firestore **必須先有對應的複合索引**，否則 `onSnapshot` 直接回 `failed-precondition`。而按照 §5.4「不對學生洩漏技術資訊」，學生只會看到「現在看不到同學的留言，晚點再來看看」——**畫面上完全看不出是壞的，只有 console 才有真正原因**。
  - **怎麼建**：第一次跑到這個查詢時，`console.warn` 出來的錯誤訊息裡就附了一個「建立索引」的直達連結，點進 Firebase Console 按建立即可（幾分鐘生效）。
  - **驗收時一定要看一次 console**：留言牆是「沒東西也很正常」的 UI，光看畫面永遠分不出「還沒有人留言」和「查詢根本失敗」。**做了留言牆就要自己送一則測試留言，確認它真的出現**。
  - 想完全避開：讓每份學習單的 feed 只放一個 qid（路徑已經帶 `worksheetId`），就不必 `where('qid','==')`，只 `orderBy('at')` 的單欄位查詢不需要複合索引。
- **「推送」與「繳交學習單」是兩個獨立動作，各自有各自的按鈕**：推送只把這一題的文字寫進 `feeds`，不影響、也不需要等待整份學習單繳交；學生可以邊寫邊推送、看同學怎麼想，最後才按「繳交學習單」把整份交給老師。**不要把推送藏在繳交按鈕裡當副作用**——那樣學生沒交卷就看不到別人、也搞不清楚兩個狀態的差別。
- **推送按鈕要防連點洗版**（2026-09-15 教師指定）：送出成功後把按鈕 `disabled` 並換成「✓ 已送出」，避免手滑連點或調皮連點灌爆留言牆；**改過輸入框內容才重新解鎖**（監聽 `input` 事件，偵測到變動就把按鈕還原成可點擊狀態），讓學生仍然可以送出修改後的版本，不是整堂課只能送一次。多題各自獨立防連點（各自的 textarea/按鈕各管各的），不要共用同一個鎖。

## 5. 教師／admin 模式標準要求

每個學習單的教師／`#admin` 工具列都要有：

1. **「預覽學生模式」按鈕＝真的變回一個全新學生，不是只把工具列藏起來**（2026-09-09 教師指定修正）：
   - **為什麼**：老師測試時一定已經填過身分、投過票、打過字。只隱藏工具列的話，看到的是「一個已經作答到一半的畫面」，**看不出學生第一次進來到底長什麼樣**——而那才是要驗收的東西（空狀態的文案、未作答的提示、進度顯示 0/N）。
   - **怎麼做**（三件事缺一不可）：
     1. **清掉這台裝置的作答快取**——身分（`wk_identity`）與這份學習單自己的作答 key 都 `removeItem`；
     2. **拿掉 `#admin` 之後整頁重載**（`location.href=location.pathname+location.search`）——不能只改變數，要讓 `IS_ADMIN` 連同所有記憶體狀態、DOM 一起重來，否則殘留的 JS state 還是會漏出來；
     3. 用 `sessionStorage` 記一個 flag，讓重載後（此時已經是學生視角）**仍然顯示「返回教師模式」浮動鍵**；按下去清掉 flag、帶回 `#admin` 再重載。
   - **動作前先 `confirm()`**：這會清掉資料，要讓老師知道再按。
2. **登入一次就好；而且不可以被匿名登入蓋掉**（2026-09-10 教師回報修正，兩條一起才有效，只做一條沒用）：
   - **進 `#admin` 不要無條件跳密碼框**：Firebase Auth 預設就把 session 持久化在本機，所以要**先 `onAuthStateChanged` 等一次目前狀態**，已經是非匿名且有 email 的使用者就直接沿用，沒有才問帳密。注意 `auth.currentUser` 在剛 `firebase.auth()` 之後**同步讀是 `null`**（session 還在非同步還原中），只能用 `onAuthStateChanged` 判斷，不能直接讀 `currentUser`。
   - **學生端不可以無條件呼叫 `signInAnonymously()`**：它不是「補一個匿名身分」，而是**把目前登入者換成匿名使用者並覆蓋本機持久化的 session**。老師從 `#admin` 按「預覽學生模式」時走的正是學生分支，這一呼叫就把教師登入洗掉了，於是「返回教師模式」永遠要重新登入。**正確寫法：先 `onAuthStateChanged` 確認真的沒有任何登入狀態，才簽名匿名。**
   ```js
   // 學生分支（非 #admin）——先確認沒登入過，才匿名登入
   var unsub=auth.onAuthStateChanged(function(u){
     if(unsub)unsub();unsub=null;
     if(u)initFeed();                                   // 已有 session（可能是老師自己的）→ 沿用，別蓋掉
     else auth.signInAnonymously().then(initFeed).catch(function(){initFeed();});
   });
   ```
   - 同理，任何「臨時要有身分才能寫入」的地方（例如推送留言）都應該走 `ensureAuth()` 這種**有才用、沒有才登入**的寫法，不要每次都重新登入。
3. **標準答案只有一個來源＝學習單自己**（2026-09-09 教師定案）：正解寫在學習單的 `data-correct`／內建資料結構／`#admin` 介面裡，**評分平台不再提供逐題手填標準答案的欄位**。理由是同一份答案維護在兩個地方一定會漂移，而且拖曳、圖形這類非純文字的答案本來就只有學習單自己判得動。教師端只負責「分數怎麼算」（配分、扣分、開放題佔比）與 AI 評分規準。
4. **不對學生洩漏技術/除錯資訊**：任何學生看得到的文字（空狀態、錯誤訊息、留言牆讀取失敗…）一律用**對小學生友善的話**（例如「現在看不到同學的留言，晚點再來看看」），**不得出現**「Firestore」「規則」「部署」「API」這類技術詞——這些只寫進 `console.warn`，給開發者/老師事後查，不顯示在畫面上。這也呼應「不必要的註解／說明」的通則：**使用者看得到的每一句話都要有存在的理由，技術實作細節不是說給學生聽的**。
5. **有留言牆（§4）的話，「還原」要一併清空，讓下一堂課從空白開始**（2026-09-15 教師指定）：老師按「↩ 還原」（回到未公布狀態）時，除了把 `revealed` 寫回 `false`，也要把這份學習單 `feeds/{worksheetId}/messages` 底下的訊息**整批刪除**（`.get()` 全部文件後用 `db.batch()` 逐筆 `delete()`，數量不多時不必分段）。**先 `confirm()`**（這會清掉留言，要讓老師知道再按）。這個動作只在真正上線、有 `db`/`quizRef` 的分支做；`teacherOffline()` 單機測試模式沒有共用資料庫，不必做。權限上 `firestore.rules` 的 `feeds` 區塊本來就是 `allow delete: if isTeacher()`（見 §4），這裡不需要額外開權限。
6. **每一題旁邊都要有「切換題型」按鈕，讓教師能現場調整體驗／檢測／開放**（2026-09-21 教師定案，此後所有新學習單一律照此實作）：
   - **為什麼**：題型該標哪一種常常要等**真的上課、看到題目難度與時間**才知道（例如原本想當體驗題暖身，結果班上普遍答得不錯，臨時想升級成正式檢測；或反過來太難了臨時降級不計分）。寫死在 HTML 裡代表每次調整都要改程式碼重新發布，不符合實際教學節奏。
   - **怎麼做**：
     1. 每題的題號/標籤旁放一個小按鈕（僅 `#admin` 且教師登入通過後才顯示，學生端完全看不到），**點一下切換一次**，依「體驗 → 檢測 → 開放 → 體驗…」三態循環（對應 §2 的 `experience`／`score`／`open`）。
     2. 目前題型即時寫回 Firebase（例如 `quizzes/{quizId}` 文件的 `qtypeOverrides:{qid:type}` 欄位，`merge:true`），透過既有的 `onSnapshot` 同步給所有裝置（含學生端），不需要額外開一條資料流。
     3. 學生端讀到 `qtypeOverrides` 後，**繳交時依教師當下設定的題型分流**到 `scoreAnswers`／`experienceAnswers`／`openAnswers`（`open` 一律送原始文字給 AI，不做自動核對），而不是在頁面寫死每題的 `qtypes[qid]`。
     4. 沒有被教師調整過的題目要有**預設題型**（通常就是 `experience`，呼應「先體驗、非必要不計分」的預設定位），`qtypeOverrides` 只存「被改過的」那幾題即可，不必每題都寫。
   - **加分題（`bonusQids`）不受影響**：加分標記是疊在題型之上的另一個維度（見 §2-b），切換題型只改變 `score`/`experience`/`open` 三選一，不會讓一般題變成加分題，也不會讓加分題被拿掉加分標記。
   - **一題有多個輸入框（例如一題兩個空格）時，切換鈕控制整題**：把底下的子欄位（如 `q4a`／`q4b`）當同一組一起切換、一起寫入 `qtypeOverrides`，避免同一題一半是體驗一半是檢測，造成完成度/正確率算法自相矛盾。
7. **教師工具列要有「檢視答案」按鈕，且評分平台要能一鍵開啟某位學生的作答重現畫面**（2026-09-21 教師定案，此後所有新學習單一律照此實作；因應題型越來越多元——投票、拖曳、畫線、正則核對……評分平台表格裡的原始 qid/value 已經不夠直覺，要看「這位學生當時實際畫面長怎樣」才判斷得快）：
   - **檢視答案**：`#admin` 工具列加一顆「👁 檢視答案」按鈕，點下去**直接把資料庫裡目前的正確答案抓回來、填進學習單本身的作答欄位**（該選的選項會被選起來、該畫線的地方會被標起來）——不是另開一個彈窗列清單。來源包含已上傳到 Firebase 的（如 `surveyPatterns`／`answers` 覆寫值）與寫死在頁面 JS 裡、不可上傳修改的（如固定的分類正解），兩種都要填。**「↩ 還原」要一併清空這些填進去的內容**（不是只清 Firestore 的 `revealed` 旗標）：把「檢視答案」寫進的欄位值/勾選狀態重設為空，讓老師按一次還原就回到乾淨畫面，不必額外切去「👀 預覽學生模式」（那個是給「重現全新學生視角」用的，會連身分欄一起清掉，跟這裡「只清答案預覽」的情境不同，見 §5-1）。
   - **檢視學生繳交（唯讀重現）**：
     1. 學習單自己的 JS 要能認得網址參數 `?review={submissions 文件 id}`：只有在 `IS_ADMIN`（`#admin`）且教師登入通過後才去 Firestore 讀那筆 `submissions` 文件並套用，避免任何人用猜的文件 id 就看到別人的作答。
     2. 套用時**不要重新觸發** `submitBtn` 那條路徑，而是直接把該份文件的 `answers`（§3 的扁平版）灌回頁面自己的資料結構（例如 `state.votes[i]`、`state.clauses[i]`、或直接設 `input.value`），並重新 render 一次現有的渲染函式（如既有的 `renderPassage()`），讓畫面長得跟學生當時交出來的一樣。
     3. **套用後鎖住互動**：所有作答用的 input/按鈕都要 `disabled`（或拿掉 `onclick`），避免老師在檢視時手滑改到別人的作答；同時隱藏「繳交學習單」按鈕，因為這不是給人再次作答的畫面。
     4. 畫面最上方要有清楚的橫幅標示「🔍 檢視模式（唯讀）：X年X班X號 的作答」，並提供一個「✕ 離開檢視」連結（帶回不含 `?review=` 的網址）避免老師忘記自己在檢視模式。
   - **評分平台這端**：`評分平台/teacher.html` 的每一列繳交紀錄旁邊要有「檢視」按鈕，點下去用該學習單登記的網址組出 `{url}?review={docId}#admin` 開新分頁——網址要先登記在「學習單設定」，沒有網址時按鈕要停用並提示原因，不要點了沒反應。
8. **「公布答案」可以拆成多階段，按鈕放在對應段落旁邊，而不是工具列一顆大按鈕全公布**（2026-09-21 教師定案）：
   - **為什麼**：一堂課的節奏常常是「先公布 A 段的答案討論完，再進到 B 段」。只有一顆總公布鈕的話，一按就全部攤開，配合不了分段教學；而且按鈕遠在最上面的工具列，離它要揭曉的內容很遠，老師還要上下捲。
   - **怎麼做**：
     1. **拿掉工具列那顆總「🎉 公布」**，改成每個要公布的段落**各自一顆公布鈕**，放在該段落的標題／題幹旁邊（僅 `#admin` 且登入後才顯示，學生端看不到）。
     2. 每一階段各自一個 Firebase 旗標（例如 `revealed`、`revealedWords`…），`merge:true` 寫回、透過既有 `onSnapshot` 同步給所有裝置；學生端各自監看對應旗標、各自揭曉自己那段。
     3. 每個揭曉函式要**冪等**（`if(state.revealedX)return;`），避免 `onSnapshot` 重複觸發時重跑動畫或重複計分。
     4. **「還原」一次收回全部階段**：把所有階段旗標都寫回 `false`；學生端偵測到任一旗標從 true 變回 false 就 `location.reload()` 回到全未公布狀態。
   - 單一階段的學習單維持一顆公布鈕即可，**不必為拆而拆**——看這節課有沒有「分段揭曉」的教學需求再決定。

## 6. 範例：五上 L01「假消息與目的辨識」怎麼套用

L01 是**課程的第一節**，目的是「先讓學生被自己的直覺打臉、產生查證動機」，不是正式評量——**所以全部題目都標 `experience`，沒有 `score` 題**：

| 學習單元件 | qid | 題型 | 理由 |
|---|---|---|---|
| 8 則真假投票卡 | `v1`–`v8` | `experience` | 有正確答案（真/假），但這節是體驗衝擊，不計分 |
| 危害勾選（5 項） | `harms` | `experience` | 有「預期都該勾」的正解，但仍是感受題不是評量 |
| 危害推論短文 | `essay` | `open` | 沒有標準答案，是學生自己的推論；**會送 AI 評分** |
| 你是怎麼判斷的？ | `reason` | `open`（且列在 `bonusQids`） | 開放題型的**加分題**：不進完成度、不扣分，AI 依內容給 0～3 分等級（教師可覆蓋，見 §2-b）；答案同時放 `openAnswers`（送 AI）與 `bonusAnswers`（完成提示） |

- `accuracyRate` → `null`（沒有 `score` 題）。
- `experienceCompletion` → 依 8 題投票＋1 題危害勾選是否都作答計算（`reason` 是 `bonus`，不計入分母）。
- `essay`／`reason` 各自有**獨立的「推送給同學看」按鈕**（都寫進同一個 `feeds/g5-L01/messages` 集合，用 `qid` 區分），推送成功後鎖住按鈕防連點（見 §4）；兩題下方各掛一個即時留言牆。
- `reason` 旁邊有「🎁 加分題：已完成／尚未完成」提示，不顯示分數（分數留給評分平台，見 §2）。
- `#admin` 工具列有「預覽學生模式」按鈕（見 §5-1），「還原」按鈕會一併清空留言牆（見 §5-5）。

這個對照表就是「換一個單元怎麼分類」的示範：**先問這節課的定位是體驗還是評量，再決定同一批題目該標 `score` 還是 `experience`**——不是看題目本身「有沒有正確答案」。

## 7. 生成後自檢

- 頁面最上方有識別列（年級/班級/座號，數字限制，會存 localStorage）嗎？班級有沒有防呆（不接受不合理的大數字，例如 15 以上）？
- 每個作答元素都標了題型，而且是 `score`／`experience`／`open` **三者之一**嗎？（加分題不是第四種題型，是另外用 `bonusQids` 標記，見 §2-b）分類理由是「這節課的定位」還是「題目形式」？（應該是前者）
- 送去 AI 的**只有 `openAnswers`** 嗎？有沒有不小心把 `score`／`experience` 的答案也送出去？（見《AI評分規範》§1）
- 底部有「繳交學習單」按鈕，按下**先跳確認對話框**、確認後才寫入嗎？成功後按鈕有沒有改成「重新繳交（覆蓋）」？（見 §3-b）
- 繳交**成功**後才顯示「完成獎勵」區塊（失敗分支不可顯示）嗎？教師檢視模式（`?review=`）有沒有把獎勵區一起拿掉？（見 §3-b）
- 繳交資料符合 §3 的欄位形狀（含 `answers` 扁平版＋分類 map＋計算欄位）嗎？有 `bonus` 題的話 `bonusAnswers` 有沒有漏？
- 沒有 `score` 題時，`accuracyRate` 是 `null`（不是 0 或缺欄位）嗎？
- **每一題都有 `isCorrect`（含沒作答的，要是 `false`）嗎？** 有沒有哪題因為省略而變成「空著反而不扣分」？`given` 沒值時是 `null` 而不是 `undefined` 嗎？（見 §3）
- `bonus` 題有沒有不小心算進 `experienceCompletion`？學生端有沒有顯示分數（不該顯示，分數留給老師事後判斷，見 §2）？
- 開放題若值得互相參考，是否加了即時同儕動態？**推送按鈕是否獨立於繳交按鈕**？留言長度、身分粗顆粒化、老師可刪、**送出成功後鎖住按鈕防連點**（改內容才解鎖）都做了嗎？（見 §4）
- 有留言牆的話，**自己送過一則測試留言、確認它真的出現**了嗎？（複合查詢缺索引時畫面看起來只是「還沒有人留言」，錯誤只在 console，見 §4）
- `#admin` 工具列有「預覽學生模式」嗎？按下去是**真的清快取＋去掉 `#admin` 重載**（看到全新學生畫面、進度歸零），還是只把工具列藏起來？（見 §5.1）
- 有留言牆的話，「還原」按鈕會不會一併清空留言牆（見 §5.5）？清空前有沒有 `confirm()`？
- 學生分支有沒有**無條件呼叫 `signInAnonymously()`**？（會洗掉老師的登入 session，必須先 `onAuthStateChanged` 確認沒登入過才簽名匿名，見 §5.2）
- 進 `#admin` 時，已經登入過的裝置還會再跳一次帳密框嗎？（不該跳，見 §5.2）
- 畫面上的文字有沒有洩漏技術/除錯資訊（見 §5.4）？
- 每一題旁邊有沒有教師專用的「切換題型」按鈕（體驗/檢測/開放三態循環）？切換有沒有即時同步給所有裝置、繳交時有沒有依當下題型分流到三個答案 map（見 §5.6）？學生端有沒有不小心看得到這顆按鈕？
- `#admin` 有沒有「檢視答案」按鈕，列出的答案有沒有涵蓋已上傳與寫死在程式碼裡兩種來源？學習單有沒有支援 `?review={docId}` 唯讀重現，套用後互動元件是否都鎖住、繳交按鈕是否隱藏、有沒有清楚的橫幅與離開連結？評分平台的「檢視」按鈕在學習單沒登記網址時是否正確停用（見 §5.7）？
- 有自由文字題要自動核對嗎？教師能不能在 `#admin` 直接於作答框填正則當答案（`|` 多解、留空退回「有沒有填」、無效正則 `try/catch` 不炸頁）？（見 §2-d）
- 有分段揭曉需求時，公布鈕是不是拆到各段落旁邊、各自一個 Firebase 旗標、揭曉函式冪等、還原一次收回全部階段（見 §5.8）？
- 客製 JS 頁面即使沒有用 `data-qid`/`data-qtype` 屬性，繳交出去的資料**形狀仍然一致**嗎？

### 規劃中（尚未定案，別當成已生效的規範）
- **AI 評分前先給「學習單概要」**：現況 AI 只看得到開放題自己的題幹＋學生作答，看不到整份學習單在教什麼、其他非開放題問了什麼，等於在空中樓閣裡打分。規劃在評分提示詞最前面加一段「概要＋全題目一覽（編號｜題型｜題目｜正解）」讓 AI 先進入情境。資料來源有三案（全自動／全手填／混合），**待教師選定後才實作、才寫進正式規範**。
